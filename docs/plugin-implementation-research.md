# Audio plug-in implementation references

Research date: 2026-08-17

## Recommendation

SemantiFX should borrow three small things now:

1. Use JUCE's distortion-demo lifecycle as the reference for **fixed-factor oversampling and latency compensation**, but implement the same resampling definition in the differentiable Python path before enabling it in playback.
2. Turn the existing manual `pluginval`/`auval` checks into one pinned macOS CI job, borrowing only the relevant fragments from Pamplejuce.
3. Make cross-language render equivalence a release gate for every effect type. Keep dasp-pytorch as the current EQ research basis, not as a catalog whose other effects are assumed ready.

Study BYOD's stable host-parameter slots and versioned chain state when SemantiFX actually accepts repeated or variable effect instances. Keep the current two-effect linear processor and file-spool worker until then. In particular, do **not** add an arbitrary audio graph, a modular cable UI, a new IPC transport, or the CLAP plug-in format now.

Here “CLAP” in SemantiFX means the **MS-CLAP language-audio model**. The CLAP plug-in ABI appearing in some reference projects is unrelated.

There is also a licensing gate before source reuse: as of the research date, SemantiFX has no top-level `LICENSE` or `COPYING` file. Oliver should choose and document the project's license before third-party code is copied into it. Until then, prefer API/design concepts, external tools, and JUCE code already governed by the project's existing JUCE license. GPL projects below are for study, not copying into an ambiguously licensed repository.

## Why these are the relevant seams

The current product is one EQ and one distortion in either order; the distortion is intentionally base-rate, the Python worker runs outside the real-time path, and validation is documented but manual ([architecture](architecture.md), [plug-in README](../plugin/README.md), [validation record](plugin-validation.md)). That makes distortion parity, audio-thread safety, and repeatable validation immediate. Arbitrary effect counts, external plug-in hosting, branching graphs, and distribution packaging are later seams.

## 1. JUCE 8.0.8: fixed chain, oversampling, and state/UI primitives

**Exact implementation to study.** SemantiFX already pins JUCE 8.0.8, so use the matching commit's [`DspModulePluginDemo::DistortionProcessor`](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L1010-L1099), [`juce::dsp::Oversampling`](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/processors/juce_Oversampling.h#L40-L151), and [`juce::dsp::DryWetMixer`](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/processors/juce_DryWetMixer.h#L50-L113). The demo also shows a compile-time [`dsp::ProcessorChain`](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L1458-L1475), APVTS state copy/replace, and cached parameter references rather than repeated string lookup ([source](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L233-L250)).

**Why it is useful now.** The distortion example initializes every oversampler from the maximum block size, upsamples only around the nonlinear waveshaper, downsamples into the output block, delays the dry path by the wet latency, and reports the processor latency ([source](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L1021-L1075)). JUCE explicitly documents that oversampling buffers must be initialized before processing and that its possibly fractional latency must be compensated and reported to the DAW ([API](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/processors/juce_Oversampling.h#L113-L151)). `DryWetMixer` already owns the latency-compensated dry delay and smooth mix gains ([API](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_dsp/processors/juce_DryWetMixer.h#L50-L113)).

**Borrow this pattern.** Start with one fixed factor, probably 2x, selected at build/design time. Allocate and call `initProcessing(maximumBlockSize)` in `prepareToPlay`; run only the nonlinear portion at the higher rate; call `getLatencyInSamples`; compensate the dry distortion mix; and update host latency outside the audio callback. Keep SemantiFX's current direct two-order dispatch rather than refactoring to `ProcessorChain`, which is compile-time ordered and provides no benefit for the current two choices.

The non-negotiable addition is a matching model-side resampler and parity fixture. Current base-rate C++ and Python renders are at least aligned. A JUCE-only oversampling change would make optimization target a different transfer function from playback. Define the factor, filters, gain normalization, edge handling, and latency canonically; render identical impulse/tone/audio fixtures through Torch and C++; then gate on waveform/response error and alias-energy behavior before enabling the feature.

**Do not copy the live switching code.** In the demo, an oversampling-parameter change is observed from `processBlock()`, and `update()` calls `prepareToPlay()` to switch factor ([source](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L180-L199), [switch](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L824-L834)). That is example code, not SemantiFX's real-time-safe switching design. A later user-selectable factor should prepare a complete replacement outside the callback and swap it without deletion or allocation on the audio thread.

For state and UI, continue using APVTS raw atomic parameter reads and attachments. JUCE documents `getRawParameterValue()` as the real-time read interface, while `copyState()` and `replaceState()` take locks and must not be called from audio processing ([APVTS API](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_audio_processors/utilities/juce_AudioProcessorValueTreeState.h#L337-L404)). SemantiFX already follows that split; there is no reason to replace it.

**License/fit.** The demo source itself carries an ISC notice ([header](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/examples/Plugins/DSPModulePluginDemo.h#L1-L24)); the JUCE library is dual-licensed under commercial terms or AGPLv3 ([license](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/LICENSE.md)). JUCE is already a project dependency, but SemantiFX still needs its own license documented before source-copy decisions. **Judgment: Adopt now**, but only as a parity-paired, fixed-factor slice.

## 2. `pluginval` and Pamplejuce: validation and release mechanics

### Tracktion `pluginval`

**Exact implementation to study.** Use the official headless CLI and its existing tests rather than writing more host simulations. `pluginval` supports fixed sample-rate/block-size matrices, reproducible random seeds, repeats, randomized order, strictness 1–10, and `rtcheck` modes; it returns a failing exit status for validation errors ([CLI documentation](https://github.com/Tracktion/pluginval/blob/4c5adc2c1a9910251667152166139a0c37b953e6/docs/Command%20line%20options.md), [README](https://github.com/Tracktion/pluginval/blob/4c5adc2c1a9910251667152166139a0c37b953e6/README.md#running-in-headless-mode)). Its level-9 allocation test disables allocations around repeated `processBlock()` calls across the configured matrix and also checks NaNs, infinities, and subnormals ([test source](https://github.com/Tracktion/pluginval/blob/4c5adc2c1a9910251667152166139a0c37b953e6/Source/tests/ExtremeTests.cpp#L18-L90)); its state and parameter-thread tests exercise restoration with an open editor and simultaneous UI/host parameter changes ([test source](https://github.com/Tracktion/pluginval/blob/4c5adc2c1a9910251667152166139a0c37b953e6/Source/tests/BasicTests.cpp#L677-L810)).

**Borrow this pattern.** Pin a released `pluginval` binary in CI. On the current macOS target, build Release, run CTest, run VST3 strictness 10 with the same fixed seed and boundary block sizes already recorded in `plugin-validation.md`, enable `--rtcheck enabled` (or temporarily `relaxed` only for a diagnosed first-block initialization), and retain the log artifact. Keep `auval` as a separate AU job. This turns the current successful manual evidence into regression protection without adding more bespoke smoke tests.

**License/fit.** `pluginval` is GPLv3 ([license](https://github.com/Tracktion/pluginval/blob/4c5adc2c1a9910251667152166139a0c37b953e6/LICENSE)); invoking its released executable as a CI tool does not require linking its source into SemantiFX. **Judgment: Adopt now.**

### Pamplejuce

**Exact implementation to study.** Pamplejuce's MIT-licensed [`build_and_test.yml`](https://github.com/sudara/pamplejuce/blob/ca3cae0b288a644d11bb64651f81c2e0a7e7b942/.github/workflows/build_and_test.yml) supplies working fragments for a build matrix, CTest, a pinned `pluginval` download and strictness-10 invocation, macOS bundle signing, `pkgbuild`/`productbuild`, `notarytool`, stapling, artifact upload, and tag-triggered release ([license](https://github.com/sudara/pamplejuce/blob/ca3cae0b288a644d11bb64651f81c2e0a7e7b942/LICENSE)).

**Borrow this pattern.** Copy only the macOS build/CTest/pluginval steps now. When there is a real distribution milestone, adapt only the AU, VST3, and Standalone signing/package/notarization steps, followed by strict `codesign` verification. Do not copy its CLAP-format paths: that format is unrelated to the MS-CLAP model and is not a current SemantiFX target.

**Caveat.** Current Pamplejuce tracks JUCE 9 and C++23 and carries cross-platform, IPP, benchmark, CLAP, installer, and release concerns SemantiFX does not need ([README](https://github.com/sudara/pamplejuce/blob/ca3cae0b288a644d11bb64651f81c2e0a7e7b942/README.md)). Migrating the project into the template would churn the pinned JUCE 8/C++17 build for no product gain. **Judgment: Adopt narrow workflow fragments now; study signing/notarization at release time.**

## 3. dasp-pytorch: preserve the model-side source of truth, add skepticism

**Exact implementation to study.** SemantiFX already uses dasp-pytorch's six-section [`parametric_eq()`](https://github.com/csteinmetz1/dasp-pytorch/blob/c9ae0126e1c441979b93995da061503a0abdceff/dasp_pytorch/functional.py#L118-L272) and its ordered physical parameter ranges in [`ParametricEQ`](https://github.com/csteinmetz1/dasp-pytorch/blob/c9ae0126e1c441979b93995da061503a0abdceff/dasp_pytorch/modules.py#L124-L156). The generic `Processor` maps ordered normalized tensors into named physical values before rendering ([source](https://github.com/csteinmetz1/dasp-pytorch/blob/c9ae0126e1c441979b93995da061503a0abdceff/dasp_pytorch/modules.py#L21-L91)).

**Borrow this pattern.** Treat the named parameter order, ranges, units, topology, and render behavior as explicit effect-schema data. For every new effect, check in shared configurations and compare the differentiable render with JUCE at multiple sample rates, including silence, impulses/tones where meaningful, and representative audio. The protocol schema should remain the public truth; implementation-specific tensor ordering should stay behind the adapter.

**Caveat.** Do not choose future effects from the package surface without reading and testing the implementation. Its `advanced_distortion()` and `expander()` raise `NotImplementedError`, and `compressor()` accepts `release_ms` but its release-time computation is commented out and not used by the smoothing path ([source](https://github.com/csteinmetz1/dasp-pytorch/blob/c9ae0126e1c441979b93995da061503a0abdceff/dasp_pytorch/functional.py#L65-L115), [compressor](https://github.com/csteinmetz1/dasp-pytorch/blob/c9ae0126e1c441979b93995da061503a0abdceff/dasp_pytorch/functional.py#L275-L403)). SemantiFX's custom distortion is correctly owned locally rather than pretending the upstream one-knob `tanh` is the same effect.

**License/fit.** Apache-2.0 ([license](https://github.com/csteinmetz1/dasp-pytorch/blob/c9ae0126e1c441979b93995da061503a0abdceff/LICENSE)). **Judgment: Adopt now as the current EQ basis and parity oracle; skip wholesale effect adoption.**

## 4. SAFE: direct historical prior art for a semantic plug-in

**Exact implementation to study.** SAFE is the closest product-level predecessor found: a JUCE family of semantic EQ, compressor, distortion, harmonics, and reverb plug-ins ([repository](https://github.com/semanticaudio/SAFE/tree/f2104987326c2a35d8359912aa3a1f2647a2131d)). Its shared [`SAFEAudioProcessor`](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.h#L4-L59) owns semantic capture/analysis around an ordinary effect processor. It allocates five seconds of pre- and post-effect recording in `prepareToPlay()` ([header](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.h#L349-L356), [allocation](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.cpp#L637-L670)), then analyzes the captured buffers on an `AnalysisThread` and saves either locally or to a server ([thread](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.cpp#L21-L42), [local record](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.cpp#L388-L417)). The record contains descriptors, current parameter settings, and features of both the unprocessed and processed audio ([serialization](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.cpp#L301-L382)).

**Why it is relevant.** Its editor preserves conventional editable effect parameters, accepts descriptor text, requires the host to be playing before capture, and lets users load settings by a saved descriptor ([editor flow](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessorEditor.cpp#L168-L245)). That validates the core interaction SemantiFX is pursuing: semantic assistance can be layered around a normal audio effect without putting analysis in `processBlock()` or hiding manual controls. Study the interaction boundary and the decision to capture both sides of the effect; SemantiFX's bounded capture plus persistent worker is already the more modern implementation.

**Caveat.** The inspected head is from September 2015 ([commit](https://github.com/semanticaudio/SAFE/commit/f2104987326c2a35d8359912aa3a1f2647a2131d)), vendors old JUCE/build infrastructure, and embeds unencrypted HTTP calls to hard-coded server IPs ([upload/download](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/JuceModules/SAFE_juce_module/PluginUtils/SAFEAudioProcessor.cpp#L485-L561)). It is GPLv3 ([license](https://github.com/semanticaudio/SAFE/blob/f2104987326c2a35d8359912aa3a1f2647a2131d/GPL-V3.txt)). **Judgment: Study the product concept now; skip the code and infrastructure.**

## 5. BYOD: the best future reference for variable internal modules

**Exact implementation to study.** BYOD is a real modular JUCE product, but the most relevant part is not its arbitrary cable graph. Study [`ParamForwardManager`](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/src/state/ParamForwardManager.h) and its [slot assignment](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/src/state/ParamForwardManager.cpp#L26-L184): BYOD exposes a fixed bank of 500 forwarding parameters, groups them into 40 persistent module slots of at most 12 parameters, versions the public IDs, and restores a module's recorded slot. Its dedicated test repeatedly adds/removes processors, round-trips state, and checks old saved forwarding layouts ([test](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/src/headless/tests/ForwardingParamStabilityTest.cpp#L69-L280)). `StateManager` separately persists APVTS, processor-chain, preset, UI, and plug-in-version state ([source](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/src/state/StateManager.cpp#L19-L87)).

**Why it is relevant later.** A host-visible parameter list cannot casually change when a user inserts a second instance of the same internal effect. BYOD demonstrates one concrete solution: stable public slots mapped onto changing internal parameters, plus tests for saved-session compatibility. Its editor also creates/removes one module component in response to chain broadcasts rather than making the UI own DSP lifetime ([board source](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/src/gui/pedalboard/BoardComponent.cpp#L30-L132)).

**What not to borrow yet.** SemantiFX's near-term chain is linear, supplied, and fixed during optimization. BYOD's 500 parameters, arbitrary routing, undoable cable graph, custom arena, and module store would impose a solution before SemantiFX has decided its host-automation contract. When variable linear chains become a committed milestone, borrow the *stable-slot and versioned-state invariants* and design a smaller SemantiFX-owned interface; do not copy the whole graph.

**License/fit.** BYOD is GPLv3 and its documentation describes separate CLA/BSD arrangements for some iOS distribution ([license](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/LICENSE), [licensing notes](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/docs/Licensing.md)). Learn from the design; do not copy source unless SemantiFX's licensing is compatible or separate permission is obtained. **Judgment: Study next.**

## 6. JUCE child-process worker: useful lifecycle reference, not a reason to rewrite IPC

**Exact implementation to study.** JUCE's [`ChildProcessCoordinator`/`ChildProcessWorker`](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_events/interprocess/juce_ConnectedChildProcess.h#L38-L236) provides a launched worker, bidirectional messages, heartbeat timeouts, connection-loss callbacks, and a kill operation. The first-party AudioPluginHost uses a worker process for risky plug-in scanning and marshals work requiring the message thread through `AsyncUpdater` ([scanner source](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/extras/AudioPluginHost/Source/HostStartup.cpp#L30-L133)).

**Pattern to borrow later.** A packaged SemantiFX worker should have explicit liveness, request identity, connection-loss behavior, bounded termination, and a clean restart path. Those invariants match the current development runner's cooperative stop followed by forced worker replacement. The JUCE classes do not supply Python/model packaging or cooperative optimization cancellation; they are a process-lifecycle reference, not a complete inference architecture.

**Caveat.** The current atomic spool already gives progress snapshots, request/result inspectability, and cancellation without pipe back-pressure. Replacing it with JUCE IPC before the packaged worker shape is known would create churn, and the official example launches a compatible executable rather than solving Python runtime/model distribution. **Judgment: Study next when distribution packaging begins; keep the spool now.** License is the existing JUCE commercial/AGPL choice.

## Watchlist and skips

### ADAC — Skip for now, keep the design lesson

ADAC's pipeline traverses a differentiable FLAMO graph into a JSON intermediate representation, generates FAUST, and exports a JUCE plug-in; its integration test renders the source and generated implementations and compares their impulse responses ([README](https://github.com/cucuwritescode/adac/blob/6045856b214ed22e14c1b8342312a709d50dc47a/README.md), [IR comparison](https://github.com/cucuwritescode/adac/blob/6045856b214ed22e14c1b8342312a709d50dc47a/tests/integration/test_ir_comparison.py)). That canonical-IR-plus-equivalence-test shape is exactly the right long-term answer to dual-implementation drift.

Do not adopt ADAC today. It labels itself beta, and its supported modules are currently delay, gain/matrix, SOS/biquad/SVF, composition, and feedback constructs—not dasp-pytorch's ParametricEQ plus SemantiFX's distortion ([supported modules](https://github.com/cucuwritescode/adac/blob/6045856b214ed22e14c1b8342312a709d50dc47a/README.md#supported-modules)). Its current integration test also contains developer-local FLAMO/pyFDN paths and skips when they are unavailable ([test setup](https://github.com/cucuwritescode/adac/blob/6045856b214ed22e14c1b8342312a709d50dc47a/tests/integration/test_ir_comparison.py#L26-L51)). Borrow the architectural idea, not the dependency. MIT-licensed ([license](https://github.com/cucuwritescode/adac/blob/6045856b214ed22e14c1b8342312a709d50dc47a/LICENSE)).

### Other tempting directions — Skip

- **`AudioProcessorGraph`:** JUCE 8 has a thoughtful wait-free render-sequence handoff: it builds/preallocates a new sequence off the audio thread, try-lock swaps pointers at the next block, and deletes the old sequence later on a timer ([implementation](https://github.com/juce-framework/JUCE/blob/d6181bde38d858c283c3b7bf699ce6340c050b5d/modules/juce_audio_processors/processors/juce_AudioProcessorGraph.cpp#L1546-L1704)). This is worth revisiting for branching or hosted third-party plug-ins, not for two owned processors in a linear chain.
- **Neural Amp Modeler plug-in and real-time inference templates:** NAM is a useful in-process model-loading product, with staged model/IR objects and a versioned unserialization path ([staging](https://github.com/sdatkinson/NeuralAmpModelerPlugin/blob/16be869746b8915885c7a35bafdcc0061faeb50e/NeuralAmpModeler/NeuralAmpModeler.cpp#L603-L633), [loading](https://github.com/sdatkinson/NeuralAmpModelerPlugin/blob/16be869746b8915885c7a35bafdcc0061faeb50e/NeuralAmpModeler/NeuralAmpModeler.cpp#L744-L781), [state migration](https://github.com/sdatkinson/NeuralAmpModelerPlugin/blob/16be869746b8915885c7a35bafdcc0061faeb50e/NeuralAmpModeler/Unserialization.cpp)). It is iPlug2, runs inference on the audio path, and does not demonstrate a packaged Python sidecar or cooperative long-running cancellation, so its central tradeoffs are the opposite of SemantiFX's asynchronous suggestion workflow. Skip it as an implementation template.

## YAGNI boundary

The next engineering sequence should be:

1. Add a small cross-language render fixture format and comparison runner for the existing EQ/distortion and both orders.
2. Define one fixed oversampling contract and make both Torch and JUCE pass those fixtures before exposing it.
3. Add one pinned macOS CI validation workflow using the existing tests, `pluginval`, and `auval`.

Stop there. Stable parameter forwarding, a generic effect registry, dynamic topology swapping, worker IPC replacement, installers, notarization, and additional plug-in formats should each wait for the product milestone that needs them.
